이 문서는 저장소 전체 문서를 어디서 무엇을 보면 되는지 안내하고, 문서마다 반복 설명하지 않는 공통 확정 규칙과 기능 개요를 한 곳에 모은다. 여기 규칙이 다른 문서와 충돌하면 이 문서가 아니라 구현 코드가 기준이다.

1. 프로젝트 한 줄 설명

비기술 사용자가 자연어로 고객 DB(SOC 보안 / Global Sales)를 조회하고, 결과를 허용된 위젯(차트·표·KPI 등)으로 받은 뒤, 프로젝트마다 1개인 Stage(핀보드)에 배치·저장하는 에이전트 MVP. 완성된 공유 대시보드 템플릿을 자동 생성하는 것은 목표가 아니다.

문서 업로드·엔티티 추출·문서 채팅·그래프 화면은 독립 doc2graph로 이동했다. 최소 그래프 기반은 backend/app/graph_backend.py에만 남겼으며 기본 미사용·UI 비표시다. 로컬 실행은 .env.local과 sql2widget-local Compose 이름으로 새 데이터를 사용한다. 토큰 issuer/브라우저 설정 키도 앱별로 분리했다.

4. 공통 확정 규칙

4.1 제품 규칙

  1. 동등한 데모 두 세계 — SOC 보안(dbconn_demo)과 Global Sales(dbconn_global)는 하나가 메인이고 다른 하나가 곁다리인 관계가 아니다.
  2. 핀보드지 포스터가 아니다 — 성공은 질문에 맞는 위젯이 채팅에 나오고 사용자가 몇 개를 Stage에 꽂는 것. 완성된 공유 대시보드 템플릿 자동 생성은 목표가 아니다.
  3. 카탈로그 가구, 사용자 배치 — 에이전트는 후보 위젯을 제안하고, 배치는 사용자가 한다.
  4. 닫힌 타입, 열린 값 — 차트 종류·레이아웃 문자열·색상(hex/CSS/HTML)을 에이전트가 지어내지 않는다. 데이터 값은 열려 있어도 컬럼 형태는 닫혀 있다.
  5. 프로젝트 스코프 — Stage는 프로젝트당 1개. 전역 대시보드 라이브러리가 아니다.

4.2 기술/아키텍처 규칙

  • 백엔드: Python, FastAPI, psycopg, 순수 SQL. ORM 없음.
  • 프론트: Vite, React, JavaScript. TypeScript 없음.
  • 상태관리 3원칙:

1. 서버 fetch → useSWR 2. 전역 UI 슬롯 → useStore (SWR 캐시 래퍼, Provider/SWRConfig 금지) 3. 입력·드래그 중 즉시성이 필요한 로컬 상태 → useState

  • 로컬 기동 기준: Docker Compose.
  • Stage 레이아웃: react-grid-layout.
  • 고객 DB는 읽기 전용 SELECT만. 앱이 DML을 실행하지 않는다.
  • 위젯 컴포넌트 이름은 서버 화이트리스트(ALLOWED_COMPONENTS) 검증. 목록 밖 이름은 채팅에서는 DataTable 폴백, Stage 저장은 400으로 거부.
  • 채팅 응답은 항상 실 LLM 호출로만 만든다(OpenAI-compatible). 키가 없거나 호출이 실패하면 키워드 매칭 등으로 추측해서 대신 답하지 않고 에러를 그대로 반환한다 — 에러를 성공한 것처럼 위장하지 않는다.
  • 감사 로그에는 행위만 남긴다. 사용자 데이터를 수정하는 쿼리는 없다.

4.3 보안/운영 규칙

  • 서비스 DB(tenants, users, projects, …)와 고객 DB(SOC/Global/Northwind 등)를 같은 커넥션·같은 쿼리 경로로 섞지 않는다.
  • 모델이 서비스 DB에 임의 SQL을 실행하게 하지 않는다.
  • 고객 DB 비밀번호·API 키를 로그에 남기지 않는다. APP_SECRET으로 암호화해 저장한다.
  • 화이트리스트 밖 컴포넌트 이름을 새로 만들지 않는다.
  • 근거 없는 해결 방안(보고서용 텍스트 등)을 지어내지 않는다.
  • 합의 없이 DML, ORM, TypeScript, SWR Provider 패턴을 도입하지 않는다.
  • 완성된 대시보드 템플릿을 기본 성공 조건으로 바꾸지 않는다.
  • 운영 배포 시 개발용 기본 비밀번호를 쓰지 않는다 (deployment/README.md 참고).

4.4 문서 동기화 규칙

코드를 바꾸는 에이전트가 직접 문서를 갱신한다. "나중에 문서화"로 미루지 않고 같은 작업 안에서 끝낸다.

5. 문서 작성 컨벤션 (이번 문서화 작업 공통)

새로 만드는 docs/01-folder-structure.md, docs/features/*.md, docs/progress.md, docs/dashboard.html, docs/kanban.html에 공통 적용한다.

  • 언어: 한국어. 코드 식별자·경로는 원문 그대로.
  • 새 파일명은 영문 kebab-case (01-folder-structure.md, features/chat.md). 기존 한국어 파일명(기능명세서.md 등)은 대체되며 신규 명명 규칙을 따르지 않는다.
  • 기능 문서는 docs/기능명세서.md의 관례를 유지: 기획이 아니라 현재 동작하는 구현이 기준. 코드와 문서가 다르면 코드가 맞다.
  • docs/progress.md의 상태 라벨은 4종으로 고정: 완료 / 진행 중 / 검증 대기 / 계획. 각 행은 영역 | 항목 | 내용 | 칸반 4열이며 영역은 칸반 필터가 된다. 칸반 열은 표시/미표시로, 기능 단위 항목만 표시하고 세부 변경 기록은 미표시로 둔다.

F-02 세션 복원 / 토큰 갱신

  • 앱 시작 시 access_token이 있으면 GET /api/auth/me 호출 → 성공하면 워크스페이스, 실패하면 로그인 화면.
  • API 응답이 401이고 retry가 참이며 refresh 토큰이 있고 경로가 /auth/*가 아니면, frontend/src/api.js가 /api/auth/refresh로 한 번 갱신 후 원 요청을 재시도한다. 동시에 여러 요청이 401을 받아도 refresh 호출은 1회로 합쳐진다(refreshPromise 공유).
  • 갱신도 실패하면 토큰을 지우고 로그인 화면으로 돌아간다.
  • 일반 API 요청 타임아웃은 15초(timeoutMs 기본값). /api/chat만 150초로 별도 지정한다(§ chat.md 참고 — 실 LLM 응답 + SQL 재시도 여유).

  • DELETE /api/conversations/{id} — 대화와 그 메시지만 삭제. 프로젝트 Stage에 이미 추가된 위젯은 유지(Stage는 프로젝트 소유, 대화 소유가 아니므로).
  • 활성 대화를 삭제하면 남은 대화 목록의 첫 번째로 자동 전환, 없으면 빈 채팅 화면.

프로젝트 삭제

  • 프로젝트 행에 마우스를 올리거나 키보드 포커스를 두면 삭제(×) 버튼을 표시한다. 활성 프로젝트는 항상 표시하고, viewer에는 표시하지 않는다.
  • 프로젝트 제목과 삭제 범위를 확인 창에 안내하며, 취소하면 삭제하지 않는다.
  • DELETE /api/projects/{id} — 서비스 DB에서 본인 프로젝트와 모든 대화·메시지, Stage·위젯을 한 트랜잭션으로 삭제한다. 채팅 벡터 DB의 해당 대화 메시지 사본도 정리하며, 벡터 DB 정리 실패 시 서비스 DB 삭제를 롤백한다. 두 DB의 커밋은 별개이므로 서비스 DB의 최종 커밋이 실패하면 벡터 사본만 먼저 삭제될 수 있다. 다른 프로젝트는 유지된다.
  • viewer 요청은 HTTP 403, 존재하지 않거나 다른 소유자·테넌트의 프로젝트는 HTTP 404다.
  • 활성 프로젝트를 삭제하면 프로젝트·대화 선택과 입력을 초기화하고 관련 화면 캐시를 비운다. 삭제 실패 시 프로젝트 행에 오류를 표시한다. UI에서는 응답 생성 중인 활성 프로젝트의 삭제 버튼을 비활성화한다.

DB 선택과 질문

POST /api/chat 입력은 conversation_id, message, 선택적 connection_id, route다. route는 data_query / schema_qa / general_chat을 허용한다. 프로젝트와 대화는 로그인한 본인의 리소스만 접근한다.

  • data_query: 허용 스키마와 유사 예상 질문을 참고해 필요한 SQL 데이터셋을 생성·실행한다. 실행된 결과의 컬럼·타입·행 수를 받은 뒤 여러 위젯과 컬럼 연결을 선택하고 위젯을 각각 생성한다. 데이터 없는 위젯 정의를 반환하며 실제 표시 데이터는 각 위젯이 별도 조회 API에서 가져온다.
  • schema_qa: 현재 연결한 DB의 허용 테이블·컬럼·키 구조를 전체 메시지 본문으로 답한다. 테이블별 설명과 필요한 컬럼 표를 본문에 표시하며 SQL·예상 질문 검색·MarkdownBlock 위젯을 생성하지 않는다. 응답 Artifact는 {type: "answer", widgets: []}다.
  • general_chat: 인사·잡담·일반 지식·개념 설명을 최근 대화 문맥과 함께 처리한다. SQL 자체의 일반 개념 설명도 이 경로다. 실 LLM의 전체 답변을 메시지 본문에 직접 표시하며 SQL·예상 질문 검색·위젯은 생성하지 않는다. 고객 DB의 스키마 조회는 분류 이후 DB 경로에서만 실행하므로 일반 대화는 고객 DB 접속을 요구하지 않는다. 처리 내역에는 “일반 대화 (DB 조회 아님)”으로 표시한다.
  • 의도가 불분명하면 위 세 경로의 선택지를 반환한다. TypeSafe Jev 실패 시 채팅 LLM이 판단하며, LLM도 실패하면 HTTP 502다.
  • 문서 질문·그래프 구성 경로와 문서 그래프 참조는 없다. schema_linking.py는 큰 DB에서 유사 질문과 이전 대화 SQL이 사용한 허용 테이블을 전달하고, 매칭이 없으면 전체 허용 스키마를 전달한다.
  • SQL 생성·실행·위젯 형식 실패를 다음 작업 판단에 전달한다. 실패한 SQL 수정은 전체 허용 스키마를 사용하며, 호환되지 않는 위젯은 실행 결과에 맞게 다시 선택한다. 완료되지 않으면 앞서 생성한 위젯을 보존하고 미완료 사유와 경로 선택지를 안내한다.

설명 답변 표시

  • 설명은 채팅 본문에 직접 표시한다. 제목·목록·강조·인라인 코드·코드 블록·간단한 Markdown 표를 지원하며 HTML은 실행하지 않고 텍스트로 표시한다. 본문 표는 데이터 조회 위젯이 아니므로 Stage 추가 버튼이 없다.
  • 과거 채팅의 MarkdownBlock도 본문으로 표시한다. 함께 저장된 데이터 위젯과 경로 선택지는 유지하고, 표시할 위젯이 없는 답변에는 Widget/JSON 영역을 숨긴다. 기존 메시지·Stage 데이터를 일괄 변경하지 않으며 이미 Stage에 저장된 MarkdownBlock은 기존 렌더러로 표시한다.
  • SOC 데모 공격 질문에 고정 Mock 문서 출처(해결 방안 본문·SourceList 위젯)를 붙이던 기능은 2026-10-14 제거했다. 데이터 조회 답변에 문서 출처를 붙이지 않는다.
  • 이번 변경은 테스트·검증용 빌드·브라우저 검증을 아직 실행하지 않았다. 사용자 승인 후 필요한 범위만 검증한다.

계획·실행·평가 루프

  • agent_plan.py가 원래 요청 전체와 최근 대화를 받아 목표·단계(예상 경로·질의·기대 결과)를 만든다. 계획당 최대 20단계이며 여러 질문은 별도 단계로 처리한다. 단일 단계는 사용자 원문을 유지한다. 사용자가 경로를 직접 선택하면 계획 호출 없이 해당 경로의 1단계 계획을 쓴다.
  • agent_service.py는 계획 → 단계별 의도 분류 → 실행 → 원래 목표 평가 → 부족한 작업 재계획을 수행한다. 데이터 단계 안에서는 data_agent.py가 실제 도구 호출마다 결과 상태를 갱신하고 모델이 다음 호출을 결정한다. 계획·분류·평가는 같은 ROUTE_CRITERIA를 사용한다. Jev/LLM은 예상 경로를 그대로 강제하지 않고 현재 하위 질문을 다시 판단하며 원래 요청은 문맥 해석에 사용한다.
  • 같은 요청 안에서 완료한 단계의 본문·위젯 정의도 다음 단계의 대화 문맥으로 전달한다. DB 하위 질문의 임베딩은 그 하위 질문으로 생성하며 원래 질문과 동일할 때만 기존 벡터를 재사용한다.
  • 마지막 단계까지 실행한 뒤 단일 단계도 원래 사용자 요청 전체·목표·실제/예상 경로·기대 결과·전체 답변·위젯 정의·검증된 SQL의 컬럼/행 수로 평가한다. 실제 결과 행은 모델에 보내거나 저장하지 않는다. 유효한 조회의 0행 결과도 완료될 수 있으며 원시 데이터가 없다는 이유만으로 추가 작업을 만들지 않는다. 모델이 목표 충족을 확인해야 완료한다.
  • 부족한 구체적 작업이 있으면 최대 5회 재계획한다. 사용자가 직접 고른 경로에서는 그 경로 안에서만 재계획하며 다른 경로가 필요하면 미완료와 선택지를 반환한다. 같은 (예상 경로, 질의) 반복, 180초 시간 예산, 요청 전체의 데이터 도구 호출 100회 상한, 경로 확인 필요 시 중단한다. 단계 수도 100개로 제한한다. LLM 호출 타임아웃은 남은 예산과 60초 중 작은 값이며 Jev/DB/임베딩의 자체 제한 시간은 별도다.
  • 여러 단계의 본문·위젯 정의를 합쳐 반환하며 Stage에는 자동 배치하지 않는다. 데이터 도구 실패는 루프에서 수정할 수 있으며 계속할 작업이 없거나 반복·한도·목표 미충족이면 부분 결과와 “요청을 완료하지 못했습니다”, 사유·세 경로 선택지를 반환한다. 최초 계획·분류·일반/구조 답변의 모델 실패는 HTTP 502다.
  • 처리 내역에는 계획·경로 단계·실제 도구 호출 순서·평가·재계획·종료 사유를 저장한다. SQL 데이터셋 수, 생성 위젯 수, 데이터 도구 호출 수, 다음 작업 판단 호출 수를 구분한다. 공개 실행 기록의 조회 ID·컬럼 이름·행 수는 저장하되 임시 결과 프로필의 SQL 전체·타입·실제 행과 원시 오류는 표시용 meta에 복사하지 않는다. 진행 스트리밍은 없고 최종 응답만 반환한다. 프런트 채팅 대기 한도는 360초다.

위젯 선택과 SQL 생성 분리

  • data_plan.generate_sql: 조회 목적에 맞는 독립 데이터셋 queries[{title,purpose,sql}]을 생성한다. 위젯 종류·개수·인덱스를 입력 계약으로 요구하지 않으며 여러 집계가 필요하면 복수 SQL을 반환한다. 서버가 query_id를 부여한다. 조회는 데이터 단계당 최대 20개다.
  • execute_sql: 지정한 조회 ID의 SELECT를 실행하고 결과 컬럼·PostgreSQL 타입·행 수·행 제한을 상태에 기록한다. 0행도 컬럼 메타데이터를 유지한다. 같은 실행 결과는 요청 메모리에서 재사용하며 각 위젯 생성 때문에 SQL을 다시 실행하지 않는다.
  • data_plan.select_widgets: 실행 완료한 조회 ID만 받는다. 실제 컬럼·타입과 요청 목적에 맞는 위젯을 여러 개 선택하고 column_map으로 위젯 역할을 연결한다. 예: {"label":"country","value":"product_revenue"}. 같은 SQL로 DataTable과 BarChart를 함께 만들 수 있다. 요청이 단일 위젯을 명시하면 이를 존중한다.
  • widget_bindings.py가 필수 역할·허용 역할·실제 컬럼 존재를 검증한다. 수치 역할은 수치 컬럼만 허용하며 단일 레코드 위젯은 복수 행을 임의 축약하지 않는다. DataTable·FilterBar·DetailCard는 원래 컬럼을 보존하고 빈 연결을 사용한다. 기존 연결 정보 없는 SQL 위젯의 별칭 동작은 유지한다.
  • create_widget: 선택한 widget_id 하나를 생성하고 상태를 갱신한다. 위젯마다 별도로 호출하며 데이터 단계당 최대 20개다. 결과 상태에서 추가 조회·수정·위젯 재선택·추가 생성이 필요하면 다음 호출을 결정한다.
  • finish는 조회·표현 목적이 충족되었을 때 선택한다. 서버도 생성 결과 존재, 모든 SQL 실행 완료, 모든 선택 위젯 생성 완료, 각 데이터셋의 위젯 존재를 확인한다. 미실행/미생성 상태로 조기 종료할 수 없다. 다음 작업이 없으면 incomplete로 종료한다. 실제 호출 수와 재계획 횟수는 서로 다르며 데이터 조회 경로가 하나여도 여러 호출을 수행한다.
  • SQL 수정은 데이터 단계당 최대 5회이며 수정한 데이터셋에 연결된 선택·생성 결과를 무효화하고 재실행 후 다시 선택한다. 같은 상태에서 동일 호출이 3번 반복되거나 조기 완료 판단이 2번 반복되면 진행 불가로 중단한다. 기존 예상 질문 카탈로그의 SQL·위젯 계획은 참고 자료로 유지한다.
  • 계획·다음 작업 판단·SQL 생성·위젯 선택·목표 평가가 별도 모델 호출이므로 호출 수·응답 시간이 늘어난다. 이번 변경의 테스트·검증용 빌드·브라우저 검증은 실행하지 않았으며 사용자 승인 후 필요한 범위만 수행한다.

SQL과 위젯

고객 DB는 SELECT/WITH 기반 읽기 전용 조회만 허용한다. 역할별 테이블 접근 권한과 서버 위젯 화이트리스트를 검증한다. 지원 위젯은 widgets-artifact.md를 본다.

대화 문맥과 후속 질문

  • 서버는 소유자 확인을 마친 현재 대화에서 최근 20개 메시지 범위의 응답 완료 이력을 구성한다(backend/app/chat_flow.py). 사용자의 현재 메시지는 이력에 중복해서 넣지 않는다.
  • 같은 연결 DB의 질문·답변 본문과 위젯 종류·제목·SQL·컬럼 연결·Markdown 본문을 Jev/LLM 라우터, 데이터 작업 판단·SQL 생성/수정·위젯 선택, 테이블 구조 답변·일반 대화에 전달한다. 직전 응답 경로도 라우터에 전달하되 현재 요청의 경로를 강제하지 않는다. “그중 상위 5개만”, “지난달과 비교해줘”, “그 컬럼은?” 같은 후속 질문을 이 문맥으로 해석한다.
  • 과거 메시지는 지시어 해석용 참고이며 현재 사실·스키마·권한의 근거가 아니다. 고객 DB 조회는 현재 허용 스키마와 읽기 전용 검증을 따르고 매번 현재 데이터를 조회한다. 의미를 확인할 수 없는 지시어는 추측하지 않고 추가 설명을 요청한다. 원시 진단 meta와 위젯 결과 행은 모델 이력에 복사하지 않는다.
  • 새 어시스턴트 메시지의 meta에 실제 connection_id를 저장해 새로고침 후에도 같은 DB의 문맥을 이어간다. 다른 DB의 응답이나 연결 DB를 확인할 수 없는 과거 메시지를 만나면 거기서 이력을 끊는다. 기존 DB 정보 없는 메시지는 화면에는 남지만 모델 문맥에서 제외한다. 응답 없이 실패한 질문도 문맥에서 제외한다. DB 이력을 소급 변환하지 않는다.
  • 이력 구성 자체는 추가 모델 호출 없이 수행한다. 계획·목표 평가·자동 재계획의 호출과 중단 조건은 위 루프 명세를 따른다. 응답은 최종 결과만 반환하며 스트리밍은 없다.
  • 입력창은 Enter 전송·Shift+Enter 줄바꿈을 유지하고, 한글 등 IME 조합 중 Enter는 전송하지 않는다.

저장과 AI 설정

질문을 전송하면 서버 저장 전에는 임시 말풍선을 표시한다. 서버는 응답 생성 전에 질문을 저장하므로 SWR의 포커스 복귀·재연결 조회에서 질문이 먼저 나타날 수 있다. 전송 전 메시지 ID 목록에 없던 동일 내용의 사용자 메시지가 조회되면 임시 말풍선만 숨기고 응답 대기 표시는 유지한다. 과거의 같은 질문은 그대로 표시하며 임시 질문·대기 표시는 전송한 대화에서만 표시한다. 중복 표시 회귀 테스트는 작성했고 사용자 승인 전에는 실행하지 않았다.

대화 메시지·Artifact의 위젯 정의·표시용 처리 내역은 서비스 DB에 저장한다. SQL 위젯의 조회 결과 데이터는 저장하지 않고 query_ref에 원본 DB ID와 SQL을 보관한다. 채팅 미리보기는 위젯별 데이터 API로 현재 데이터를 조회한다(widgets-artifact.md). 처리 내역에는 경로·모델·SQL 테이블 선택·유사 질문·복구 결과를 표시하며 meta의 connection_id는 문맥의 DB 범위를 확인하는 데 사용한다. API 키·원시 오류·참조 SQL 계획은 표시용 meta에 저장하지 않는다.

기존 메시지 임베딩 저장·검색과 related_messages 응답은 A에 유지한다. 예상 질문용 question_catalog와는 별개다. 프런트엔드는 related_messages를 아직 표시하지 않는다.

Provider별 브라우저 AI 설정은 sql2widget_ai_settings에 보관하고 X-LLM-* 헤더로 요청한다. 모델 키가 없거나 호출이 실패하면 추측 응답 대신 오류를 표시한다.

같은 설정의 Provider 공통 jevApiKey는 AI 설정 패널의 Jev API key 입력란에서 저장하고 채팅의 X-Jev-API-Key 헤더로만 전달한다. 요청 키를 우선 사용하며 빈 값·헤더 생략 시 서버 TYPESAFE_API_KEY를 사용한다. Jev 키는 모델 프롬프트나 대화 기록에 저장하지 않는다. 길이·줄바꿈 형식 오류는 메시지를 저장하기 전에 HTTP 400으로 거부한다. 자세한 동작은 Jev 의도 분류 연결을 따른다.

F-09 Artifact 표시

채팅은 필요한 SQL 데이터셋을 먼저 생성·실행하고 실제 컬럼·타입·행 수를 받은 뒤 여러 위젯을 선택한다. 같은 결과를 여러 위젯이 공유할 수 있으며 위젯마다 column_map으로 역할을 연결한다. 예를 들어 국가·제품·매출 조회 하나로 원본 DataTable과 국가별 매출 BarChart를 만들 수 있다. 실제 도구 호출마다 결과를 받아 다음 작업을 결정하고 각 위젯을 별도로 생성한다. 여러 단계 결과는 하나의 Artifact로 모으며 아래 데이터 없는 정의·위젯별 현재 조회 방식은 유지한다. 자세한 흐름은 채팅 명세를 따른다.

  • MarkdownBlock 설명을 본문으로 옮긴 뒤 표시할 위젯이 남아 있을 때만 Widget / JSON 세그먼트 토글이 뜬다(AssistantAnswer). artifact_id만 있는 빈 Artifact에는 표시하지 않는다. JSON 복사는 화면에 남은 위젯 정의를 대상으로 한다.
  • 테이블 구조 설명은 전체 채팅 본문으로 반환하며 테이블별 설명·컬럼 표를 본문에서 읽는다. 새 설명 답변은 MarkdownBlock을 생성하지 않는다. 과거 채팅의 MarkdownBlock은 본문에 표시하고, 이미 Stage에 저장된 항목은 호환성을 위해 기존 렌더러로 표시한다. 기존 저장 데이터는 수정하지 않는다.
  • Widget 뷰: 위젯마다 ArtifactPreviewCard — 제목, 렌더러, (가능하면) SQL 보기 토글, "Add to stage" 버튼.
  • 채팅 미리보기 카드는 테두리·제목을 포함해 높이 320px로 고정한다. 제목 아래 남은 공간을 조회 영역·정적 위젯·SQL 패널이 채우며 새로고침 버튼은 조회 영역 안에 포함된다. Stage·Viewer 위젯은 기존 배치 높이를 따른다.
  • JSON 뷰: Artifact의 위젯 정의를 pretty-print. 조회 결과 행·차트 데이터·KPI 값은 포함하지 않는다.
  • JSON 뷰의 "JSON 복사" 버튼은 화면에 표시한 Artifact JSON 전체를 들여쓰기와 함께 클립보드에 복사한다. 복사 중에는 중복 클릭을 막고 성공·실패 안내를 복사 버튼 바로 왼쪽에 10px 글자로 표시한다. 클립보드 접근이 불가능하면 JSON을 선택해 직접 복사하도록 안내한다. 읽기 전용 사용자도 복사할 수 있다.
  • SQL 보기 가능 여부(canShowSql)는 widget.sql/widget.query_ref.sql/widget.props.__query_ref.sql/widget.props.__sql 중 하나가 있거나, 컴포넌트가 SQL 지원 목록(KpiStat, DataTable, RankList, BarChart, LineChart, PieChart, FilterBar, KpiSparkline, PieTable, BarTable, StackedBarChart, Heatmap, ScatterChart, Histogram, CompareCard, PivotTable, StatusSummary, EventTimeline, KpiGroup, DetailCard, HorizontalBarChart, ComboChart, BoxPlot, Treemap)에 속할 때다. MarkdownBlock/SourceList는 SQL 없음.
  • 실제 SQL 문자열은 resolveWidgetSql()이 반환한다: 위젯에 백엔드가 직접 붙인 sql/query_ref.sql/props.__query_ref.sql/props.__sql만 보여준다 — 없으면 빈 문자열이고 SQL 토글이 숨는다. 추측한 SQL을 대신 보여주지 않는다(2026-09-22, 옛 FALLBACK_BY_TITLE/FALLBACK_BY_COMPONENT 하드코딩 테이블 삭제).
  • 미리보기 카드는 draggable(SQL 보기 중이거나 viewer면 제외). viewer는 드래그 핸들도, "Add to stage" 버튼도 없다.

위젯별 데이터 조회 (2026-10-13)

  • SQL 위젯 정의는 component, title, sql, query_ref: {connection_id, sql}, 표시 설정 props와 ID만 저장한다. rows, categories, series, points, cells, bins, KPI value 등 조회 결과는 Artifact·Stage에 새로 저장하지 않는다. MarkdownBlock·SourceList의 본문/출처와 SQL 없는 과거 FilterBar의 칩은 유지한다. 새 FilterBar는 SQL 조회 위젯이다.
  • 생성 루프는 실행한 SQL 결과를 요청 메모리에서 공유한다. _materialize_plan은 이 결과에 컬럼 연결을 적용해 각 위젯의 데이터 형식을 확인하며 같은 SQL을 위젯마다 다시 실행하지 않는다. 실제 행은 저장하지 않는다. 실제 표시 데이터는 각 QueryWidget이 SWR로 별도 조회한다. 화면을 열거나 새로고침 버튼을 누르면 현재 데이터를 가져오며, 주기적인 폴링은 없다.
  • props.column_map은 데이터 값이 아닌 컬럼 연결 설정이다. 예: {"label":"country","value":"product_revenue"}. Artifact·Stage·Viewer·JSON 복사에서 이를 보존하고 조회 API가 현재 SQL 결과에 적용한다. 같은 SQL을 참조하는 여러 위젯도 서로 다른 연결을 사용할 수 있다. 기존 연결 정보 없는 위젯은 원래 별칭 변환을 유지한다.
  • 채팅 미리보기는 GET /api/conversations/{conversation_id}/widgets/{widget_id}/data, Stage·Viewer는 GET /api/projects/{project_id}/stage/widgets/{widget_id}/data를 호출한다. 응답은 {props, count}이며 브라우저 메모리 캐시에만 보관하고 HTTP 캐시는 no-store다.
  • 서버가 저장된 위젯의 SQL·원본 DB로 조회한다. 브라우저가 SQL·DB를 요청 인자로 보내지 않으며 현재 DB 선택창 변경도 기존 위젯의 조회 DB를 바꾸지 않는다. 소유자·tenant·현재 역할의 테이블 권한을 매 요청 검사하고 기존 SELECT 검증·1000행 제한·10초 SQL 제한을 적용한다. 테이블 권한이 없으면 403이고 데모 권한으로 대체하지 않는다.
  • 위젯마다 로딩·빈 결과·조회 오류·다시 조회를 표시한다. DB 연결 오류의 원문/접속 자격증명은 응답하지 않는다. 데이터 새로고침은 LLM을 호출하지 않는다.
  • 기존 저장 결과는 DB 일괄 마이그레이션 없이 읽을 때 데이터 필드를 제외한다. 채팅은 메시지 meta의 DB ID, Stage는 소유한 원본 Artifact·위젯의 같은 SQL에서 DB ID를 복원한다. SQL이나 원본 DB를 확인할 수 없으면 409로 질문 재실행을 안내하며 다른 DB로 추측 조회하지 않는다. Stage를 새로 저장하거나 수정하면 데이터 없는 정의로 저장한다.

TanStack Charts 적용 범위 (2026-10-13)

  • 기존 BarChart의 categories[], series[0].data[] 실행 시점 props 계약을 유지하며 첫 번째 시리즈만 표시한다. 저장 JSON은 위젯별 조회 정의로 바뀌었다. 여러 시리즈의 기여도는 신규 StackedBarChart로 표시한다.
  • tanstackBarChart.js·tanstackAnalyticalCharts.js·tanstackCatalogCharts.js가 고정된 차트 정의를 만든다. LLM이 임의의 TanStack 정의·색상·차트 타입을 생성하는 경로는 없다.
  • 채팅 미리보기·Stage·Viewer가 같은 렌더러를 공유한다. 카드의 너비와 높이 변화는 라이브러리의 ResizeObserver가 처리하고, 툴팁은 포인터와 키보드로 확인할 수 있다.
  • 중복 항목명은 별도 막대로 유지한다. 0·음수·소수·숫자 문자열을 표시하고, 누락된 값은 기존처럼 0으로 처리한다. 숫자가 아닌 값은 막대에서 제외한다.
  • 프런트 테스트 14개, 신규 위젯 백엔드 테스트 26개, Vite 빌드와 브라우저 화면의 크기 변경·빈 결과·키보드 툴팁·StrictMode 재마운트를 확인했다. 로컬 Compose를 띄운 뒤 백엔드 전체 124개 테스트가 통과했다. 실제 Global Sales 데모 DB의 SELECT 결과로 신규 4종을 만들고 Stage 추가/재조회 API 및 Viewer 화면을 확인했다(6개월 누적 매출, 지역·제품 24셀, 판매량·매출 288관측, 매출 9구간). 이 실데이터 화면은 SQL 직접 검증 결과이며 AI가 생성한 응답이 아니다. 서버·현재 브라우저에 AI 키가 없어 실 LLM 호출은 아직 미검증이다.
  • Recharts와 함께 사용하므로 빌드의 압축 JS는 최초 적용 전 218.59KB에서 4종 추가 후 264.54KB로 증가했다. 기존 BarChart 적용 대비 추가 증가는 약 4.2KB다.

F-11 Stage 배치 / 저장

  • 데스크톱에서는 채팅과 Stage 사이 경계선을 드래그하거나, 경계선에 포커스를 두고 좌우 방향키로 너비를 조절한다. 채팅 최소 320px, Stage 최소 340px이며 더블클릭으로 기본 비율을 복원한다. 비율은 현재 화면에서만 유지되고 새로고침 시 초기화된다. 960px 이하에서는 기존 세로 배치를 유지한다.
  • 프로젝트당 Stage 1행. GET .../stage 호출 시 없으면 생성(get_or_create_stage).
  • 레이아웃 엔진은 react-grid-layout(12열, rowHeight: 36, margin: [12,12], compactType: "vertical").
  • 이동·리사이즈(onLayoutChange)는 500ms 디바운스 후 변경된 위젯들만 PATCH .../stage/widgets/{id}로 저장(persistLayout). 저장 중에는 로컬 상태(localWidgets)를 먼저 갱신해 즉시 반영하고, 실패하면 저장 상태를 error로 표시한다.
  • 전체 교체: PUT .../stage { widgets: [...] } (현재 UI는 이 경로를 안 쓰고 있으나 API는 열려 있음).
  • 단건 수정: PATCH — title/props/query_ref/layout 중 보낸 필드만 갱신. 레이아웃 수정은 조회 정의를 유지하며 데이터 결과는 저장하지 않는다.
  • 삭제: DELETE .../stage/widgets/{id}.
  • 새로고침 시 서버에서 위젯 정의·레이아웃을 복원하고, 각 위젯의 데이터 API를 호출해 현재 데이터를 표시한다. 위젯별 새로고침 버튼도 같은 API를 호출한다. 주기적 폴링은 없다.
  • 빈 Stage 안내: 편집 가능 역할 "대화의 결과 위젯을 여기로 드래그하세요", viewer "배치된 위젯이 없습니다."
  • 저장 상태 표시줄(대기 / 저장 중… / 저장됨 / 저장 실패)은 전역 슬롯 storeKeys.ui(useStore)에 있다. 편집 불가 역할(readOnly)에는 표시하지 않는다.
  • 위젯 크기는 minW:2, minH:2로 제한.

예상 질문 유사도 DB

AI 설정을 저장한 뒤 DB를 선택하고 예상 질문 생성을 누른다. 테이블 접근 역할을 고르거나 생성 개수를 지정하지 않는다. AI가 선택한 DB의 모든 테이블을 묶음별로 살펴보고 다양한 예상 질문과 SQL·위젯을 만든다. 코드는 읽기 전용 SQL을 검증하고 유효한 AI 질문만 임베딩해 저장한다. 진행률과 질문 수를 보여주며 중단되면 이어서 진행할 수 있다. 채팅에서는 기존 사용자 테이블 접근 제한을 적용한다. 예상 질문 유사도 상세.

유사도 기준은 코사인 유사도 0.75 이상, 기본 상위 5개다. 점수가 높아도 질문이 동일하다는 보장은 없으므로 LLM이 조건·날짜·집계·정렬을 현재 질문과 스키마에 맞춰 재검토한다. 검색 결과가 없거나 검색에 실패하면 LLM이 현재 스키마로 계획을 생성한다. LLM 호출 자체가 실패하면 기존 채팅처럼 오류를 반환한다.

저장 구조와 접근 범위

기존 chat_vector DB의 question_catalog 테이블을 사용한다. 채팅 로그용 message_embeddings와 별도다. 003_question_catalog.sql은 기존 command_catalog 테이블과 컬럼을 이름만 바꿔 데이터를 보존한다.

각 항목에는 tenant_id, connection_id, 자연어 question, 그 질문의 임베딩, plan(SQL·위젯 컴포넌트·제목), DB 이름·테이블 목록, 전체 DB 스키마 해시, 임베딩 모델 식별자와 등록 시각이 저장된다. 비밀번호·API 키·조회 결과 행은 저장하지 않는다. 동일 고객·DB·스키마·모델에서 같은 질문을 다시 등록하면 기존 항목을 갱신한다.

예상 질문 등록은 역할별로 나누지 않는다. 선택한 DB의 전체 조회 가능 테이블을 대상으로 한 번 생성한다. 채팅에서 검색할 때는 현재 로그인 사용자의 기존 테이블 접근 권한으로 SQL 참조를 다시 검사한다. 다른 고객·DB의 질문은 검색되지 않는다. 스키마가 바뀌면 새 스키마 기준으로 다시 생성해야 한다.

  2. 4개 테이블씩 AI에 스키마를 전달해 예상 질문과 SQL·위젯을 생성한다. 코드에서

  1. 생성된 SQL을 현재 고객 DB에서 읽기 전용으로 검증한다. 실행할 수 없는 질문은 건너뛰고

skipped_count로 알린다. 질문을 만들지 못한 테이블은 uncovered_tables에 표시한다. 다른 질문 의도를 AI에 추가 요청하고, 빠진 테이블은 다시 요청한다. 유효한 AI 질문만 묶음으로 임베딩해 저장한다.

  1. 화면에 테이블 진행률과 등록된 질문 수를 보여준다. 중단되면 같은 DB에서 다시 눌러 이어간다.

조건·날짜·값의 조합은 무한하므로 가능한 모든 문장을 미리 저장할 수는 없다. 이 로직은 조회 가능한 모든 테이블을 처리하고, 스키마로 의미가 있는 다양한 질문을 추가한다. 저장된 질문과 가까운 새 질문은 LLM이 현재 조건에 맞게 답변을 만든다.
