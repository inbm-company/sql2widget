## DB 선택과 질문

`POST /api/chat` 입력은 `conversation_id`, `message`, 선택적 `connection_id`, `route`다. route는 `data_query` / `schema_qa` / `general_chat`을 허용한다. 프로젝트와 대화는 로그인한 본인의 리소스만 접근한다.

- `data_query`: 허용 테이블의 실제 스키마와 예상 질문의 SQL·위젯 계획을 실 LLM에 전달하고 읽기 전용 SQL과 데이터 형식을 검증해 데이터 없는 위젯 정의를 생성한다. 실제 표시 데이터는 각 위젯이 별도 조회 API에서 가져온다.
- `schema_qa`: 현재 연결한 DB의 허용 테이블·컬럼·키 구조를 답한다.
- `general_chat`: 인사·잡담·일반 지식·개념 설명을 최근 대화 문맥과 함께 처리한다. SQL 자체의 일반 개념 설명도 이 경로다. 실 LLM의 전체 답변을 메시지 본문에 직접 표시하며 SQL·예상 질문 검색·위젯은 생성하지 않는다. 고객 DB의 스키마 조회는 분류 이후 DB 경로에서만 실행하므로 일반 대화는 고객 DB 접속을 요구하지 않는다. 처리 내역에는 “일반 대화 (DB 조회 아님)”으로 표시한다.
- 의도가 불분명하면 위 세 경로의 선택지를 반환한다. TypeSafe Jev 실패 시 채팅 LLM이 판단하며, LLM도 실패하면 HTTP 502다.
- 문서 질문·그래프 구성 경로와 문서 그래프 참조는 없다. `schema_linking.py`는 큰 DB에서 유사 질문과 이전 대화 SQL이 사용한 허용 테이블을 전달하고, 매칭이 없으면 전체 허용 스키마를 전달한다.
- SQL/계획 실행 실패 시 전체 스키마로 한 번 수정 요청한다. 그래도 실패하면 오류를 표시한다.

## SQL과 위젯

고객 DB는 SELECT/WITH 기반 읽기 전용 조회만 허용한다. 역할별 테이블 접근 권한과 서버 위젯 화이트리스트를 검증한다. 지원 위젯은 [widgets-artifact.md](widgets-artifact.md)를 본다.

기존 SOC 데모의 고정 `DocumentProvider` 출처 보조 기능은 유지한다. 사용자 업로드 문서나 doc2graph의 그래프를 읽는 기능은 아니다.

## 대화 문맥과 후속 질문

- 서버는 소유자 확인을 마친 현재 대화에서 최근 20개 메시지 범위의 응답 완료 이력을 구성한다(`backend/app/chat_flow.py`). 사용자의 현재 메시지는 이력에 중복해서 넣지 않는다.
- 같은 연결 DB의 질문·답변 본문과 위젯 종류·제목·SQL·Markdown 본문을 Jev/LLM 라우터, SQL 계획·1회 복구, 테이블 구조 답변·일반 대화에 전달한다. 직전 응답 경로도 라우터에 전달하되 현재 요청의 경로를 강제하지 않는다. “그중 상위 5개만”, “지난달과 비교해줘”, “그 컬럼은?” 같은 후속 질문을 이 문맥으로 해석한다.
- 과거 메시지는 지시어 해석용 참고이며 현재 사실·스키마·권한의 근거가 아니다. 고객 DB 조회는 현재 허용 스키마와 읽기 전용 검증을 따르고 매번 현재 데이터를 조회한다. 의미를 확인할 수 없는 지시어는 추측하지 않고 추가 설명을 요청한다. 원시 진단 meta와 위젯 결과 행은 모델 이력에 복사하지 않는다.
- 새 어시스턴트 메시지의 meta에 실제 `connection_id`를 저장해 새로고침 후에도 같은 DB의 문맥을 이어간다. 다른 DB의 응답이나 연결 DB를 확인할 수 없는 과거 메시지를 만나면 거기서 이력을 끊는다. 기존 DB 정보 없는 메시지는 화면에는 남지만 모델 문맥에서 제외한다. 응답 없이 실패한 질문도 문맥에서 제외한다. DB 이력을 소급 변환하지 않는다.
- 대화 문맥을 전달하기 위한 추가 모델 호출은 없다. 여러 단계 계획·목표 평가·자동 재계획은 포함하지 않는다. 응답은 기존처럼 최종 결과만 반환하며 스트리밍은 없다.
- 입력창은 Enter 전송·Shift+Enter 줄바꿈을 유지하고, 한글 등 IME 조합 중 Enter는 전송하지 않는다.

## 저장과 AI 설정

대화 메시지·Artifact의 위젯 정의·표시용 처리 내역은 서비스 DB에 저장한다. SQL 위젯의 조회 결과 데이터는 저장하지 않고 `query_ref`에 원본 DB ID와 SQL을 보관한다. 채팅 미리보기는 위젯별 데이터 API로 현재 데이터를 조회한다([widgets-artifact.md](widgets-artifact.md)). 처리 내역에는 경로·모델·SQL 테이블 선택·유사 질문·복구 결과를 표시하며 meta의 `connection_id`는 문맥의 DB 범위를 확인하는 데 사용한다. API 키·원시 오류·참조 SQL 계획은 표시용 meta에 저장하지 않는다.

기존 메시지 임베딩 저장·검색과 `related_messages` 응답은 A에 유지한다. 예상 질문용 `question_catalog`와는 별개다. 프런트엔드는 related_messages를 아직 표시하지 않는다.

Provider별 브라우저 AI 설정은 `sql2widget_ai_settings`에 보관하고 `X-LLM-*` 헤더로 요청한다. 모델 키가 없거나 호출이 실패하면 추측 응답 대신 오류를 표시한다.

같은 설정의 Provider 공통 `jevApiKey`는 AI 설정 패널의 `Jev API key` 입력란에서 저장하고 채팅의 `X-Jev-API-Key` 헤더로만 전달한다. 요청 키를 우선 사용하며 빈 값·헤더 생략 시 서버 `TYPESAFE_API_KEY`를 사용한다. Jev 키는 모델 프롬프트나 대화 기록에 저장하지 않는다. 길이·줄바꿈 형식 오류는 메시지를 저장하기 전에 HTTP 400으로 거부한다. 자세한 동작은 [Jev 의도 분류 연결](admin.md#jev-의도-분류-연결)을 따른다.
