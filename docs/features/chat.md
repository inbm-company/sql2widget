## DB 선택과 질문

`POST /api/chat` 입력은 `conversation_id`, `message`, 선택적 `connection_id`, `route`다. route는 `data_query` / `schema_qa` / `general_chat`을 허용한다. 프로젝트와 대화는 로그인한 본인의 리소스만 접근한다.

- `data_query`: 허용 스키마와 유사 예상 질문을 참고해 필요한 SQL 데이터셋을 생성·실행한다. 실행된 결과의 컬럼·타입·행 수를 받은 뒤 여러 위젯과 컬럼 연결을 선택하고 위젯을 각각 생성한다. 데이터 없는 위젯 정의를 반환하며 실제 표시 데이터는 각 위젯이 별도 조회 API에서 가져온다.
- `schema_qa`: 현재 연결한 DB의 허용 테이블·컬럼·키 구조를 전체 메시지 본문으로 답한다. 테이블별 설명과 필요한 컬럼 표를 본문에 표시하며 SQL·예상 질문 검색·`MarkdownBlock` 위젯을 생성하지 않는다. 응답 Artifact는 `{type: "answer", widgets: []}`다.
- `general_chat`: 인사·잡담·일반 지식·개념 설명을 최근 대화 문맥과 함께 처리한다. SQL 자체의 일반 개념 설명도 이 경로다. 실 LLM의 전체 답변을 메시지 본문에 직접 표시하며 SQL·예상 질문 검색·위젯은 생성하지 않는다. 고객 DB의 스키마 조회는 분류 이후 DB 경로에서만 실행하므로 일반 대화는 고객 DB 접속을 요구하지 않는다. 처리 내역에는 “일반 대화 (DB 조회 아님)”으로 표시한다.
- 의도가 불분명하면 위 세 경로의 선택지를 반환한다. TypeSafe Jev 실패 시 채팅 LLM이 판단하며, LLM도 실패하면 HTTP 502다.
- 문서 질문·그래프 구성 경로와 문서 그래프 참조는 없다. `schema_linking.py`는 큰 DB에서 유사 질문과 이전 대화 SQL이 사용한 허용 테이블을 전달하고, 매칭이 없으면 전체 허용 스키마를 전달한다.
- SQL 생성·실행·위젯 형식 실패를 다음 작업 판단에 전달한다. 실패한 SQL 수정은 전체 허용 스키마를 사용하며, 호환되지 않는 위젯은 실행 결과에 맞게 다시 선택한다. 완료되지 않으면 앞서 생성한 위젯을 보존하고 미완료 사유와 경로 선택지를 안내한다.

## 설명 답변 표시

- 설명은 채팅 본문에 직접 표시한다. 제목·목록·강조·인라인 코드·코드 블록·간단한 Markdown 표를 지원하며 HTML은 실행하지 않고 텍스트로 표시한다. 본문 표는 데이터 조회 위젯이 아니므로 Stage 추가 버튼이 없다.
- 과거 채팅의 `MarkdownBlock`도 본문으로 표시한다. 함께 저장된 데이터 위젯과 경로 선택지는 유지하고, 표시할 위젯이 없는 답변에는 Widget/JSON 영역을 숨긴다. 기존 메시지·Stage 데이터를 일괄 변경하지 않으며 이미 Stage에 저장된 `MarkdownBlock`은 기존 렌더러로 표시한다.
- SOC 데모 공격 질문에 고정 Mock 문서 출처(해결 방안 본문·`SourceList` 위젯)를 붙이던 기능은 2026-10-14 제거했다. 데이터 조회 답변에 문서 출처를 붙이지 않는다.
- 이번 변경은 테스트·검증용 빌드·브라우저 검증을 아직 실행하지 않았다. 사용자 승인 후 필요한 범위만 검증한다.

## 계획·실행·평가 루프

- `agent_plan.py`가 원래 요청 전체와 최근 대화를 받아 목표·단계(예상 경로·질의·기대 결과)를 만든다. 계획당 최대 20단계이며 여러 질문은 별도 단계로 처리한다. 단일 단계는 사용자 원문을 유지한다. 사용자가 경로를 직접 선택하면 계획 호출 없이 해당 경로의 1단계 계획을 쓴다.
- `agent_service.py`는 계획 → 단계별 의도 분류 → 실행 → 원래 목표 평가 → 부족한 작업 재계획을 수행한다. 데이터 단계 안에서는 `data_agent.py`가 실제 도구 호출마다 결과 상태를 갱신하고 모델이 다음 호출을 결정한다. 계획·분류·평가는 같은 `ROUTE_CRITERIA`를 사용한다. Jev/LLM은 예상 경로를 그대로 강제하지 않고 현재 하위 질문을 다시 판단하며 원래 요청은 문맥 해석에 사용한다.
- 같은 요청 안에서 완료한 단계의 본문·위젯 정의도 다음 단계의 대화 문맥으로 전달한다. DB 하위 질문의 임베딩은 그 하위 질문으로 생성하며 원래 질문과 동일할 때만 기존 벡터를 재사용한다.
- 마지막 단계까지 실행한 뒤 단일 단계도 원래 사용자 요청 전체·목표·실제/예상 경로·기대 결과·전체 답변·위젯 정의·검증된 SQL의 컬럼/행 수로 평가한다. 실제 결과 행은 모델에 보내거나 저장하지 않는다. 유효한 조회의 0행 결과도 완료될 수 있으며 원시 데이터가 없다는 이유만으로 추가 작업을 만들지 않는다. 모델이 목표 충족을 확인해야 완료한다.
- 부족한 구체적 작업이 있으면 최대 5회 재계획한다. 사용자가 직접 고른 경로에서는 그 경로 안에서만 재계획하며 다른 경로가 필요하면 미완료와 선택지를 반환한다. 같은 (예상 경로, 질의) 반복, 180초 시간 예산, 요청 전체의 데이터 도구 호출 100회 상한, 경로 확인 필요 시 중단한다. 단계 수도 100개로 제한한다. LLM 호출 타임아웃은 남은 예산과 60초 중 작은 값이며 Jev/DB/임베딩의 자체 제한 시간은 별도다.
- 여러 단계의 본문·위젯 정의를 합쳐 반환하며 Stage에는 자동 배치하지 않는다. 데이터 도구 실패는 루프에서 수정할 수 있으며 계속할 작업이 없거나 반복·한도·목표 미충족이면 부분 결과와 “요청을 완료하지 못했습니다”, 사유·세 경로 선택지를 반환한다. 최초 계획·분류·일반/구조 답변의 모델 실패는 HTTP 502다.
- 처리 내역에는 계획·경로 단계·실제 도구 호출 순서·평가·재계획·종료 사유를 저장한다. SQL 데이터셋 수, 생성 위젯 수, 데이터 도구 호출 수, 다음 작업 판단 호출 수를 구분한다. 공개 실행 기록의 조회 ID·컬럼 이름·행 수는 저장하되 임시 결과 프로필의 SQL 전체·타입·실제 행과 원시 오류는 표시용 meta에 복사하지 않는다. 진행 스트리밍은 없고 최종 응답만 반환한다. 프런트 채팅 대기 한도는 360초다.

## 위젯 선택과 SQL 생성 분리

- `data_plan.generate_sql`: 조회 목적에 맞는 독립 데이터셋 `queries[{title,purpose,sql}]`을 생성한다. 위젯 종류·개수·인덱스를 입력 계약으로 요구하지 않으며 여러 집계가 필요하면 복수 SQL을 반환한다. 서버가 `query_id`를 부여한다. 조회는 데이터 단계당 최대 20개다.
- `execute_sql`: 지정한 조회 ID의 SELECT를 실행하고 결과 컬럼·PostgreSQL 타입·행 수·행 제한을 상태에 기록한다. 0행도 컬럼 메타데이터를 유지한다. 같은 실행 결과는 요청 메모리에서 재사용하며 각 위젯 생성 때문에 SQL을 다시 실행하지 않는다.
- `data_plan.select_widgets`: 실행 완료한 조회 ID만 받는다. 실제 컬럼·타입과 요청 목적에 맞는 위젯을 여러 개 선택하고 `column_map`으로 위젯 역할을 연결한다. 예: `{"label":"country","value":"product_revenue"}`. 같은 SQL로 DataTable과 BarChart를 함께 만들 수 있다. 요청이 단일 위젯을 명시하면 이를 존중한다.
- `widget_bindings.py`가 필수 역할·허용 역할·실제 컬럼 존재를 검증한다. 수치 역할은 수치 컬럼만 허용하며 단일 레코드 위젯은 복수 행을 임의 축약하지 않는다. DataTable·FilterBar·DetailCard는 원래 컬럼을 보존하고 빈 연결을 사용한다. 기존 연결 정보 없는 SQL 위젯의 별칭 동작은 유지한다.
- `create_widget`: 선택한 `widget_id` 하나를 생성하고 상태를 갱신한다. 위젯마다 별도로 호출하며 데이터 단계당 최대 20개다. 결과 상태에서 추가 조회·수정·위젯 재선택·추가 생성이 필요하면 다음 호출을 결정한다.
- `finish`는 조회·표현 목적이 충족되었을 때 선택한다. 서버도 생성 결과 존재, 모든 SQL 실행 완료, 모든 선택 위젯 생성 완료, 각 데이터셋의 위젯 존재를 확인한다. 미실행/미생성 상태로 조기 종료할 수 없다. 다음 작업이 없으면 `incomplete`로 종료한다. 실제 호출 수와 재계획 횟수는 서로 다르며 데이터 조회 경로가 하나여도 여러 호출을 수행한다.
- SQL 수정은 데이터 단계당 최대 5회이며 수정한 데이터셋에 연결된 선택·생성 결과를 무효화하고 재실행 후 다시 선택한다. 같은 상태에서 동일 호출이 3번 반복되거나 조기 완료 판단이 2번 반복되면 진행 불가로 중단한다. 기존 예상 질문 카탈로그의 SQL·위젯 계획은 참고 자료로 유지한다.
- 계획·다음 작업 판단·SQL 생성·위젯 선택·목표 평가가 별도 모델 호출이므로 호출 수·응답 시간이 늘어난다. 이번 변경의 테스트·검증용 빌드·브라우저 검증은 실행하지 않았으며 사용자 승인 후 필요한 범위만 수행한다.

## SQL과 위젯

고객 DB는 SELECT/WITH 기반 읽기 전용 조회만 허용한다. 역할별 테이블 접근 권한과 서버 위젯 화이트리스트를 검증한다. 지원 위젯은 [widgets-artifact.md](widgets-artifact.md)를 본다.

## 대화 문맥과 후속 질문

- 서버는 소유자 확인을 마친 현재 대화에서 최근 20개 메시지 범위의 응답 완료 이력을 구성한다(`backend/app/chat_flow.py`). 사용자의 현재 메시지는 이력에 중복해서 넣지 않는다.
- 같은 연결 DB의 질문·답변 본문과 위젯 종류·제목·SQL·컬럼 연결·Markdown 본문을 Jev/LLM 라우터, 데이터 작업 판단·SQL 생성/수정·위젯 선택, 테이블 구조 답변·일반 대화에 전달한다. 직전 응답 경로도 라우터에 전달하되 현재 요청의 경로를 강제하지 않는다. “그중 상위 5개만”, “지난달과 비교해줘”, “그 컬럼은?” 같은 후속 질문을 이 문맥으로 해석한다.
- 과거 메시지는 지시어 해석용 참고이며 현재 사실·스키마·권한의 근거가 아니다. 고객 DB 조회는 현재 허용 스키마와 읽기 전용 검증을 따르고 매번 현재 데이터를 조회한다. 의미를 확인할 수 없는 지시어는 추측하지 않고 추가 설명을 요청한다. 원시 진단 meta와 위젯 결과 행은 모델 이력에 복사하지 않는다.
- 새 어시스턴트 메시지의 meta에 실제 `connection_id`를 저장해 새로고침 후에도 같은 DB의 문맥을 이어간다. 다른 DB의 응답이나 연결 DB를 확인할 수 없는 과거 메시지를 만나면 거기서 이력을 끊는다. 기존 DB 정보 없는 메시지는 화면에는 남지만 모델 문맥에서 제외한다. 응답 없이 실패한 질문도 문맥에서 제외한다. DB 이력을 소급 변환하지 않는다.
- 이력 구성 자체는 추가 모델 호출 없이 수행한다. 계획·목표 평가·자동 재계획의 호출과 중단 조건은 위 루프 명세를 따른다. 응답은 최종 결과만 반환하며 스트리밍은 없다.
- 입력창은 Enter 전송·Shift+Enter 줄바꿈을 유지하고, 한글 등 IME 조합 중 Enter는 전송하지 않는다.

## 저장과 AI 설정

질문을 전송하면 서버 저장 전에는 임시 말풍선을 표시한다. 서버는 응답 생성 전에 질문을 저장하므로 SWR의 포커스 복귀·재연결 조회에서 질문이 먼저 나타날 수 있다. 전송 전 메시지 ID 목록에 없던 동일 내용의 사용자 메시지가 조회되면 임시 말풍선만 숨기고 응답 대기 표시는 유지한다. 과거의 같은 질문은 그대로 표시하며 임시 질문·대기 표시는 전송한 대화에서만 표시한다. 중복 표시 회귀 테스트는 작성했고 사용자 승인 전에는 실행하지 않았다.

대화 메시지·Artifact의 위젯 정의·표시용 처리 내역은 서비스 DB에 저장한다. SQL 위젯의 조회 결과 데이터는 저장하지 않고 `query_ref`에 원본 DB ID와 SQL을 보관한다. 채팅 미리보기는 위젯별 데이터 API로 현재 데이터를 조회한다([widgets-artifact.md](widgets-artifact.md)). 처리 내역에는 경로·모델·SQL 테이블 선택·유사 질문·복구 결과를 표시하며 meta의 `connection_id`는 문맥의 DB 범위를 확인하는 데 사용한다. API 키·원시 오류·참조 SQL 계획은 표시용 meta에 저장하지 않는다.

기존 메시지 임베딩 저장·검색과 `related_messages` 응답은 A에 유지한다. 예상 질문용 `question_catalog`와는 별개다. 프런트엔드는 related_messages를 아직 표시하지 않는다.

Provider별 브라우저 AI 설정은 `sql2widget_ai_settings`에 보관하고 `X-LLM-*` 헤더로 요청한다. 모델 키가 없거나 호출이 실패하면 추측 응답 대신 오류를 표시한다.

같은 설정의 Provider 공통 `jevApiKey`는 AI 설정 패널의 `Jev API key` 입력란에서 저장하고 채팅의 `X-Jev-API-Key` 헤더로만 전달한다. 요청 키를 우선 사용하며 빈 값·헤더 생략 시 서버 `TYPESAFE_API_KEY`를 사용한다. Jev 키는 모델 프롬프트나 대화 기록에 저장하지 않는다. 길이·줄바꿈 형식 오류는 메시지를 저장하기 전에 HTTP 400으로 거부한다. 자세한 동작은 [Jev 의도 분류 연결](admin.md#jev-의도-분류-연결)을 따른다.

## 응답 생성 중지

- 응답 생성 중 전송 버튼은 `■` 중지 버튼으로 바뀐다. 마우스·키보드로 실행할 수 있고 접근성 이름은 “응답 생성 중지”다. 다른 대화로 이동해도 이 버튼은 현재 진행 중인 요청을 중지한다.
- 중지는 채팅 HTTP 요청을 취소하고 대기 표시를 해제한다. 실패/시간 초과 오류나 질문 자동 재입력 대신 “응답 생성을 중지했습니다”를 해당 대화에 표시한다. 다음 질문으로 입력 중인 내용과 서버에 이미 저장된 사용자 질문은 유지한다. 로그아웃·화면 종료 시에도 진행 중 요청을 취소한다.
- 서버는 연결 종료를 감지해 요청별 취소 신호를 설정한다. 모델/Jev 호출 전후·에이전트 단계 경계·답변 저장 전에 확인해 후속 실행·재시도와 취소된 답변 저장을 막는다. 다른 요청에는 영향을 주지 않는다. 취소 처리의 서버 상태 코드는 499이며 브라우저에서는 요청 취소로 처리한다.
- 이미 진행 중인 동기 모델 호출·검색·DB 조회는 즉시 강제 종료하지 않는다. 해당 작업이 반환한 뒤 다음 경계에서 멈추므로 진행 중 호출의 비용까지 되돌리지는 않는다. 이미 완료·저장된 결과는 유지하며 완료와 중지가 겹치면 완료된 답변이 보일 수 있다. 요청 시간 제한은 중지 신호와 함께 유지한다.
- 취소 회귀 테스트는 작성했으며 실행·빌드·브라우저 확인은 사용자 승인 대기다.

## 처리 내역의 질문별 경로 표시

- SQL 조회부터 위젯 생성까지 수행하는 `data_query` 경로는 처리 내역의 요약·경로 순서·단계별 실제/예상 경로에서 “위젯 생성”으로 표시한다. 내부 경로 식별자와 분류·실행 방식은 유지하며 과거 기록에도 같은 표시명을 적용한다. 경로 번호는 하위 질문의 실행 순서이며 위젯 생성 개수나 개별 도구 호출 순서가 아니다.
- 답변 완료 후 처리 내역의 요약과 “경로 순서”에는 실제 단계 순서대로 `1. 경로 A → 2. 경로 B → 3. 경로 A`를 표시한다. 같은 경로의 연속 실행·이전 경로로 복귀도 생략하거나 합치지 않는다. 실행 경로를 모르는 과거 실패 단계는 “경로 미기록”으로 남기며 예상 경로를 실제 선택으로 대신하지 않는다. 여러 단계일 때 상단 분류 방식은 마지막 단계의 값임을 표시하고 새 기록은 각 단계의 분류 방식도 함께 표시한다.
- 실행 단계는 기본적으로 접혀 있고 “N개 단계 · 질문별 경로 보기”를 눌러 펼치거나 다시 접는다. 질문·실제 경로·예상 경로와의 차이·평가 결과·기존 상세 내역을 함께 확인한다. 종료 상태는 접어도 보인다.
- 질문은 실행 기록의 `query`를 우선 표시한다. 기존 기록에 이 값이 없으면 재계획이 없고 같은 순서의 계획 경로가 실행 기록의 예상 경로와 일치하는 경우에만 계획의 질문을 사용한다. 재계획·누락 등으로 연결을 확인할 수 없으면 “질문 내용 미기록”으로 표시하며 질문을 추측하지 않는다.
- 새 실행 기록 `meta.steps[]`에는 실제 하위 질문 `query`, 예상 경로 `expected_route`, 실제 경로 `route`, 분류 방식 `route_source`, 있는 경우 확신도 `route_confidence`, 최초 계획/재계획 차수 `plan_revision`을 남긴다. 되묻기 단계에도 질문을 기록하며 sql2widget의 부분 실패는 실패 전 확정한 경로를 보존한다. 응답·저장된 처리 내역에 동일하게 반영한다. 과거 데이터를 일괄 변환하지 않는다. 실시간 진행 표시는 추가하지 않는다.

## 질문 분리와 단계 연결

- 자동 계획은 문장 기호보다 독립적으로 요구한 결과를 기준으로 하위 질문을 나눈다. 같은 경로라도 서로 다른 질문은 별도 단계로 보존한다. 하나의 비교 결과를 요구한 질문은 비교 대상마다 나누지 않으며 날짜·조건·지표·원하는 표현 방식은 해당 질문에 유지한다.
- 사용자 요청 순서를 유지하되 뒤 질문이 앞 결과를 필요로 하면 선행 작업부터 실행한다. 계획에서는 필요한 앞 결과를 명시하고 그 값을 지어내지 않는다. 문서/DB 조회와 일반 개념 설명이 섞인 요청도 각각의 질문으로 나눌 수 있으며 매 단계 실제 경로를 다시 분류한다.
- 각 단계는 실제 하위 질문을 실행 기록에 직접 남긴다. 재계획으로 최초 계획과 실행 순서가 달라져도 질문과 경로의 연결을 유지한다. 다단계 계획에 질문이 빠졌으면 전체 원문을 임의로 복사해 여러 번 실행하지 않고 계획 오류로 처리한다. doc2graph의 다단계 질문을 500자에서 자르던 제한은 제거해 뒤 조건을 보존한다. 계획 단계 수 한도·자동 승인 금지·사용자가 직접 선택한 경로의 제약은 유지한다.
- 같은 요청 안에서 완료된 질문·답변·위젯 정의는 기존 같은 DB 대화 문맥을 통해 다음 단계에 전달한다. SQL 데이터셋·위젯 생성 도구 호출은 하위 질문 내부 작업이며 질문 분리 단계 수와 구분한다.
- 질문 분리·경로 반복/복귀·재계획·되묻기·저장 보존 회귀 테스트를 작성했다. 이번 변경의 테스트·검증용 빌드·브라우저 확인·실모델 호출은 실행하지 않았으며 다음 검증 단계로 남긴다. [작업 기록](../temp/chat-question-routing-2026-10-15.md)을 참고한다.
