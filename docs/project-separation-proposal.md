## 1. 분리 방향

**현재 sql2widget을 사용 목적에 따라 두 프로젝트로 분리한다.**

| 구분 | A. DB 위젯 프로젝트 | B. 문서 지식그래프 프로젝트 |
|------|---------------------|------------------------------|
| 사용 목적 | DB에 질문하고 조회 결과를 위젯으로 배치 | 문서에서 엔티티·관계를 추출하고 근거를 탐색·질문 |
| 입력 | 고객 DB 연결, 자연어 질문 | 문서 파일, 추출 스키마에 관한 지시, 자연어 질문 |
| 핵심 처리 | SQL 계획 → 읽기 전용 조회 → 위젯 생성 | 문서 적재 → 스키마 합의 → 엔티티 추출 → 그래프 탐색·답변 |
| 주요 결과 | 표·차트·KPI, 프로젝트별 Stage | 문서/엔티티 그래프, 원문 근거, 문서 기반 답변 |
| 주요 저장소 | 서비스 PostgreSQL, 고객 PostgreSQL, 예상 질문용 pgvector | 서비스 PostgreSQL, Neo4j. 대화 임베딩용 pgvector 제외 |
| 화면 중심 | 공통 기본 UI + DB 선택 + 채팅 + 위젯 Stage | 같은 기본 UI + 문서 소스 + 채팅 + 그래프·원문 탐색 |
| 그래프 | 최소 백엔드 기반만 보존, 당장 활용·화면 표시 없음 | 문서/엔티티 그래프가 주요 결과 화면 |
| 프로젝트 이름 | `sql2widget` | `doc2graph` |
| 로그인·프로젝트·데이터 | 각각 독립 관리 | 각각 독립 관리, 통합 로그인 없음 |
| 초기 데이터 | 새 데이터로 시작, 기존 데이터 이전 생략 | 새 문서를 업로드해 시작, 기존 그래프 이전 생략 |

독립 프로젝트의 완료 기준은 **각자 설치·실행·테스트·배포할 수 있고, 다른 프로젝트의 서버가 없어도 핵심 기능이 동작하는 것**이다. 각각 독립 저장소로 관리하고, 서로의 계정·서비스 DB·소스 디렉터리·API를 공유하지 않는다.

**양쪽 모두 채팅을 제공하고 기본 UI는 동일하게 유지한다.** 사이드바·프로젝트/대화 목록·채팅·설정 패널의 구성과 스타일을 맞추고, 결과 영역은 A의 위젯 Stage와 B의 그래프로 구분한다. B의 ‘그래프만 표시’는 결과 영역에 대한 결정이며, 채팅·문서 관리·원문 근거 확인은 포함한다.

Q1~Q6의 사용자 답변은 6절에 기록했다. A의 ‘최소 그래프’는 기존 연결·조회 기반을 선택적으로 보존하는 수준으로 구체화했다(3.2절). 이 문서의 기능 경계에 따라 코드 분리를 수행했고, 로컬 실행과 자동 검증을 완료했다. 운영 배포는 수행하지 않았다.

## 2. 현재 구현된 기능과 분리 범위

여기서 ‘구현’은 해당 코드 경로가 있다는 뜻이며, 운영에서 정상 작동하는지까지 검증했다는 뜻은 아니다.

### 2.3 양쪽에 필요한 기반 기능

| 기능 | 분리 방향 | 분리할 때 확인할 점 |
|------|------|--------------------|
| 로그인·세션·역할 | 양쪽에 각각 유지, 완전 분리 | 사용자 DB, 토큰 설정·저장 키 분리. 통합 로그인 미도입 |
| 프로젝트·대화 CRUD | 양쪽에 각각 유지 | 각 앱의 프로젝트가 독립된 소유 단위가 됨 |
| 채팅 메시지·응답 이력 | 양쪽에 유지 | A의 SQL/위젯 응답과 B의 그래프 작업/근거 응답으로 계약 정리 |
| AI 연결 설정 | 양쪽에 유지 | Provider 설정, 로컬 모델 목록, 요청 헤더, 브라우저 설정 키 |
| LLM 호출·오류·사용량 기록 | 필요한 공통 로직을 각 앱에 포함 | `llm.py`는 서비스 DB의 `llm_usage`에 쓰므로 저장소도 필요 |
| 처리 내역 표시 | 양쪽에 필요한 부분 유지 | SQL 경로 설명과 그래프 조회·전달·근거 정보를 분리 |
| 대화 메시지 임베딩 | B에서는 제외. A의 기존 동작은 유지 | Q4는 B에 대한 답변이며 A의 예상 질문 검색·기존 대화 임베딩 제거를 뜻하지 않음 |
| 디자인·API 클라이언트·상태관리 | 동일한 기본 UI를 각 프로젝트에 독립 포함 | 공통 화면 구조·스타일을 맞추고 DB/그래프 전용 기능을 분리 |

필요한 기반 코드는 각 프로젝트 안에 둔다. 공통 서버·공유 패키지·SSO 없이 같은 기존 UI에서 출발해 각각 독립 실행한다. 같은 모양의 UI를 사용하는 것과 실행 시 코드·데이터를 공유하는 것은 별개다.

### 2.4 동일한 기본 UI의 구체 범위

| 화면 요소 | 양쪽 공통 | A: sql2widget | B: doc2graph |
|-----------|-----------|---------------|--------------|
| 로그인 | 같은 레이아웃·입력/오류 표시 방식 | A 계정으로 로그인 | B 계정으로 로그인 |
| 사이드바 | 같은 프로젝트·대화 목록, 생성·이름 변경·삭제 조작 | A 프로젝트·대화 | B 프로젝트·대화 |
| 채팅 | 같은 메시지 목록·입력창·진행/오류 표시·패널 구성 | DB 질문·SQL·위젯 응답 | 그래프 구축 대화·문서 질문·근거 응답 |
| 결과 패널 | 같은 위치·기본 스타일·채팅과의 너비 조절 방식 | 위젯 Stage, 그래프 탭 없음 | 그래프·선택한 노드/원문 상세, Stage 없음 |
| 관리 패널 | 같은 패널 형태·버튼·입력 스타일 | DB 연결·테이블 권한·예상 질문 | 문서 업로드·소스·스키마·추출 관리 |
| AI 설정 | 같은 Provider 설정 UI와 오류 처리 | A 설정으로 저장 | B 설정으로 저장 |

빈 기능 탭이나 동작하지 않는 DB/Stage 버튼을 B에 남겨 외형을 맞추지 않는다. 공통 레이아웃·디자인·조작 방식을 유지하면서 기능에 따른 내용만 바꾼다.

## 3. 현재 연결되어 있는 지점과 분리 방법

### 3.1 하나의 채팅이 네 가지 기능을 처리한다

현재 `/api/chat` → `run_agent()` → 의도 라우팅으로 `data_query`, `schema_qa`, `knowledge_qa`, `graph_build`를 처리한다. `ChatRequest`에도 DB 연결과 그래프 작업 필드가 같이 있다.

- A: DB 조회·구조 질문·되묻기만 처리하도록 채팅 계약과 라우터를 정리한다.
- B: 그래프 구축·문서 질문·되묻기로 정리한다. DB 연결 선택 없이 채팅을 시작할 수 있어야 한다.
- 현재 명시적 `graph_build` 분기는 DB 처리 전에 실행되지만, 일반 라우팅과 `knowledge_qa`는 DB 연결 해석·스키마 준비를 먼저 거친다. B로 옮길 때 이 호출 순서를 해제해야 한다.
- 답변이 없을 때 제안하는 버튼도 분리한다. 현재 `graph_answer.py`는 DB 조회·DB 구조 질문 버튼을 반환할 수 있다.

근거: [main.py](../backend/app/main.py)의 `chat`, [agent_service.py](../backend/app/agent_service.py)의 `run_agent`, [contracts.py](../backend/app/contracts.py)의 `ChatRequest`, [intent_router.py](../backend/app/intent_router.py).

### 3.2 A는 문서 그래프 참조를 끊고 최소 그래프 기반만 남긴다 — Q1 반영

`schema_linking.py`는 큰 DB에서 유사 질문으로 테이블을 고르지 못하면 `project_graph.project_table_catalog()`로 문서의 `Table` 엔티티 설명을 읽고 관련 테이블을 고른다.

**확정 방향:** 기존 문서를 가져다 쓰지 않는다. A의 SQL 처리는 유사 질문 기반 선택을 유지하고, 선택하지 못하면 전체 허용 스키마를 사용한다. B의 문서·그래프 API와 연결하지 않는다. 그래프 기능의 기반은 최소한으로 남기고 UI에는 표시하지 않는다.

구현 시 ‘필요 최소한’은 다음 범위로 잡는다.

- **보존:** 기존 Neo4j 연결 생성·종료·오류 처리와 읽기 실행에 필요한 백엔드 기반. 현재 `graph_ingestion.py`의 연결 처리와 `project_graph.py`의 `_read` 등이 문서 처리와 섞여 있으므로 독립 가능한 부분만 남긴다.
- **기본 동작:** 그래프는 미사용 상태다. 연결 설정이나 그래프 서버가 없어도 A의 시작·채팅·SQL 조회·프로젝트 삭제가 정상 동작한다. 미사용 상태에서는 Neo4j 접속이나 문서 그래프 조회를 시도하지 않는다.
- **B로 분리:** 문서 업로드·청킹·스키마 협의·엔티티 추출·문서 기반 답변·그래프 화면. 이를 A의 최소 그래프에 포함하지 않는다.
- **현 단계에서 추가하지 않는 것:** 새로운 DB 스키마 그래프 자동 생성, 그래프 적재 파이프라인, B 연동 API, 공개 그래프 관리 API. 향후 실제 활용 대상이 정해지면 해당 기능을 설계한다.

이는 그래프를 전부 삭제한다는 뜻이 아니라, 당장 사용하지 않는 기반만 선택적으로 보존한다는 뜻이다. 문서 그래프를 사용한 테이블 선택이 빠지므로 큰 DB의 모델 입력량·답변 품질은 분리 후 확인한다.

### 3.3 관리 화면과 Stage가 두 기능을 함께 담고 있다

- `AdminPanel.jsx`의 DB 관리 영역에 `GraphSources`가 들어 있다. A의 DB 연결·권한·예상 질문 관리와 B의 문서 소스 관리를 각각 배치한다.
- `StageCanvas.jsx` 안에 위젯/그래프 탭이 있다. 같은 결과 패널 위치에서 A는 위젯 Stage만, B는 `ProjectGraph`와 그래프 상세만 표시한다.
- `App.jsx`에는 DB 선택, 위젯 카드, `GraphFlowCard`, 공통 채팅 처리가 섞여 있다. 파일 전체를 한쪽으로 넘기는 방식으로 끝낼 수 없다.
- `ViewerStagePage.jsx`는 Stage를 감싼다. B의 읽기 전용 조회는 Stage 저장소 없이 그래프를 볼 수 있도록 분리한다.

### 3.4 B는 채팅 답변을 유지하고 결과 영역은 그래프로 구성한다 — Q2 반영

`graph_answer.py`는 `MarkdownBlock`, `DataTable`, `SourceList`를 만들고 공통 `sanitize_artifact()`를 호출한다. 따라서 **B에서 차트·Stage를 제외하더라도 답변과 근거를 표시할 최소 렌더러·응답 검증은 필요하다.**

B에는 채팅 답변·표·출처 표시를 유지한다. 위젯 고정 버튼·Stage 드래그/배치·Stage 저장 API/테이블은 제외한다. 기존 응답 표시 코드를 필요한 만큼 사용하되, DB 차트 카탈로그 전체를 B의 기능으로 가져오지 않는다. 그래프 영역에서는 노드·관계·속성·원문 근거를 확인한다.

### 3.5 프로젝트 삭제와 서버 시작에도 그래프 의존성이 있다

`repositories/projects.py`의 프로젝트 삭제는 `graph_sources`를 조회해 문서 작업 잠금을 검사하고, 대화 임베딩도 지운다. 서비스 DB의 외래 키는 Stage를 삭제하고 문서 소스는 프로젝트 연결만 해제한다. `main.py`의 시작/종료 처리에는 중단된 추출 작업 정리와 Neo4j 연결 종료가 있다.

A에서 그래프 테이블만 제거하면 이 경로가 깨진다. A의 프로젝트 삭제에서 문서 작업 잠금을 제거하고, 미사용 그래프는 시작 시 조회하지 않도록 정리한다. B에서는 대화 임베딩 삭제를 제외하고 문서 작업 잠금·중단된 추출 복구를 유지한다. B의 미연결 소스 보존 정책은 현재 동작을 기준으로 하고, 영구 삭제 정책 변경은 별도 논의한다.

### 3.6 ‘문서’라는 이름만으로 코드를 옮기면 안 된다

`documents.py`의 현재 선택 Provider는 고정 데모 자료를 검색하는 `MockExternalDocumentProvider`다. `DatabaseDocumentProvider`와 `document_chunks` 테이블도 있지만 현재 `get_document_provider()`는 이를 선택하지 않는다. 이 경로는 사용자가 올린 문서의 Neo4j 그래프와 연결되어 있지 않다.

Q1은 기존 문서 그래프를 SQL 계획에 재사용하는 기능에 대한 답변으로 적용한다. 별개인 고정 SOC 데모 출처 기능은 기존 A 동작으로 유지하고 B에 이관하지 않는다(A11). B는 새로 올린 문서와 실제 추출 근거를 사용한다.

Q5에 따라 기존 계정·대화·Stage·문서·그래프를 이전하는 작업은 생략하고 새 저장소로 시작한다. 기존 데이터와 볼륨을 삭제하거나 덮어쓰는 작업을 의미하지 않는다. 샘플 고객 DB는 기존 시드/복원 절차로 준비할 수 있고, 새 문서 그래프는 B에서 문서를 업로드해 생성한다. A의 최소 그래프에는 기존 문서·엔티티 데이터를 복사하지 않는다.

### 4.4 실행·배포

각 프로젝트에 프런트엔드·백엔드·의존성 파일·환경변수 예시·Compose·테스트·배포 설정을 둔다. B에서 Neo4j를 사용하고, A에서 예상 질문·기존 대화 임베딩용 pgvector와 고객 DB 연결을 사용한다. A의 최소 그래프 기반에 필요한 클라이언트 의존성은 보존하되 Neo4j 서버는 기본 실행의 필수 조건으로 두지 않는다. B는 `react-grid-layout`·DB 차트용 라이브러리·pgvector를 제외할 수 있도록 최소 채팅 렌더러의 의존성을 정리한다.

현재 로컬 `docker-compose.yml`에는 Neo4j와 `db-chat-vector`가 있지만 `compose.production.yml`에는 해당 서비스 선언이 없다. 외부 서비스 사용 여부나 운영의 별도 설정은 이번 조사로 확인하지 않았다. 현재 운영 파일을 그대로 복사하면 두 프로젝트가 모두 실행된다고 가정하면 안 된다.

독립 실행 시 Compose 프로젝트명·볼륨·포트·배포 경로·이미지명·CI/CD 대상을 구분한다. 브라우저 저장 키도 앱별로 구분한다. 현재 토큰과 AI 설정은 `agent4any_*` 키를 사용하므로 특히 같은 origin의 경로를 나눠 배포하는 경우 충돌하지 않아야 한다.

저장 위치는 현재 `sql2widget/`과 같은 상위 폴더 아래 `doc2graph/`를 두는 구성으로 계획한다. 독립 doc2graph 폴더와 로컬 Git 저장소를 생성했다. 커밋·푸시·원격 저장소 생성은 수행하지 않았다.

## 7. 구현 단계의 순서와 완료 조건

1. **독립 실행 골격 준비:** `sql2widget`과 `doc2graph`의 프런트·백엔드·설정·의존성·신규 설치용 DB 스키마를 구성한다. 기존 소스와 데이터는 비교·복구 기준으로 보존한다.
2. **같은 기본 UI 구성:** 기존 로그인·사이드바·프로젝트/대화·채팅·설정 UI를 각 앱에 두고, A에는 위젯 Stage, B에는 그래프 결과 영역을 연결한다.
3. **B의 기능 연결:** 문서 관리·그래프 구축 채팅·추출·문서 답변·탐색을 연결한다. 고객 DB·Stage·대화 임베딩 의존성을 제외한다.
4. **A의 기능 정리:** DB 연결·예상 질문·SQL·위젯·Stage를 유지하고 기존 문서 그래프 참조·문서 관리 UI를 제외한다. 선택적 최소 그래프 기반은 남기되 기본 동작에서 호출하지 않는다.
5. **새 데이터 초기화:** 분리된 새 볼륨/DB로 각각 시작한다. 기존 계정·대화·위젯·문서·그래프 이전은 생략하고 초기 계정·샘플 DB·신규 문서 업로드 경로를 확인한다.
6. **각각 검증·문서화:** 아래 시나리오를 각 앱에서 확인하고 기능 명세·실행/배포 안내를 맞춘다. 운영 전환 대상·시점은 별도로 확정한다.

| 검증 대상 | 완료 조건 |
|-----------|-----------|
| A 핵심 흐름 | 로그인 → 프로젝트/대화 생성 → DB 선택 → 질문 → SQL 조회 → 위젯 → Stage 저장·새로고침 복원·Viewer 조회 |
| A 독립성·권한 | B·Neo4j 없이 기본 실행, 문서 그래프 호출·그래프 UI 없음, 최소 그래프 기반 보존, SELECT 제한·테이블 권한·프로젝트 소유권·예상 질문 검색 유지 |
| B 핵심 흐름 | 로그인 → 프로젝트 생성 → 문서 업로드·적재 → 스키마 제안·수정·승인 → 추출 → 그래프/원문 탐색 → 근거 답변 |
| B 독립성·실패 처리 | 고객 DB·Stage 테이블·pgvector 없이 실행, 승인 전 추출 차단·취소·실패·재시작 복구, 타 프로젝트/테넌트 접근 제한 |
| 공통 UI·채팅 | 같은 기본 레이아웃·스타일·조작 방식, 양쪽 채팅 입력/응답·대화 저장/복원, B에 위젯 고정 버튼이 없고 A에 그래프 탭이 없음 |
| 공통 독립성 | AI 설정·모델 실패 표시·대화 삭제·처리 내역 복원, 계정·세션·설정·볼륨 분리, 통합 로그인 없음 |
| 신규 데이터 | 각 앱을 새 데이터로 초기화 가능, 기존 볼륨에 쓰기/삭제 없음, B에서 신규 문서 업로드부터 그래프 생성 가능 |

기존 테스트 중 SQL·예상 질문·스키마 선택·Stage 관련 항목은 A로, 그래프 적재·추출·문서 답변·그래프 UI 계산 항목은 B로 배치한다. 프로젝트·대화·라우팅·처리 내역 테스트는 양쪽의 기능 계약에 맞게 나눈다. 특히 ‘반대쪽 서비스 없이 실행’ 검증을 추가해 숨은 의존성이 남지 않았는지 확인한다.

## 8. 이번 조사 결과의 사용 방법

1~2절에서 확정한 기능 배분·기본 UI를 확인하고, 3절에서 이를 코드에 적용할 경계를 살펴본다. 6절은 사용자 답변 기록이며, 4절과 7절은 구현 단계의 배치·검증 기준이다. 추가 의견은 해당 절이나 기능 ID를 기준으로 같은 문서에 반영한다.

코드·앱별 신규 스키마·로컬/운영 구성 템플릿과 문서를 분리했다. dashboard.html·kanban.html도 기능 문서·진행 상황과 동기화했다. 원래 서비스 데이터/볼륨은 삭제하지 않았고 로컬 새 볼륨만 초기화했다.
