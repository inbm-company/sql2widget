현재 구현·진행 상황·계획을 기능 영역별로 관리한다. 각 행의 `칸반` 열이 `표시`인 항목만 칸반 카드가 되고, `미표시` 항목은 이 문서와 대시보드에만 남는다. 이 문서를 고친 뒤 `python3 scripts/render_docs.py`로 칸반·대시보드를 생성한다.

상태와 칸반 열은 `완료` → `검증 대기` → `진행 중` → `다음` → `계획` → `해당없음` 순서다. `다음`은 우선 착수할 작업, `계획`은 아직 착수 순서를 정하지 않은 작업, `해당없음`은 현재 적용하지 않기로 판단한 작업이다.

## 현재 상태

앱은 로그인·프로젝트·대화, 관리자 DB 연결·테이블 권한, 질문 라우팅과 요청 계획 기반 SQL 조회, 결과에 맞는 위젯 생성, 위젯별 현재 데이터 조회, Stage 배치와 Viewer 읽기 전용 화면을 제공한다. 위젯은 결과 값 대신 원본 DB·SQL 정의를 저장하고 표시할 때마다 현재 데이터를 조회한다. 기본 Stage 배치·Viewer 화면은 별도 카드로 두지 않고 [stage.md](features/stage.md)·[viewer.md](features/viewer.md)에 유지한다.

기능 영역: 인증·프로젝트 · DB 연결 · 채팅·에이전트 · 예상 질문 · 위젯·Stage · 외부 연계 · AI 설정 · 배포·운영.

각 표시 카드의 제목은 아래 작업 상세에 연결한다. 상태·영역·칸반 표시 여부는 위 상태 표에서만 관리하고, 상세의 작업 ID는 제목·상태가 바뀌어도 유지한다. 계획의 작업 범위·완료 기준안은 검토용이며 미정 정책을 확정된 구현으로 보지 않는다.

#### 기록된 범위와 근거

2026-10-15 중지 버튼·요청 취소·서버 후속 실행/저장 차단, 회귀 테스트 작성. 테스트·빌드·브라우저 검증 미실행. [기능](features/chat.md#응답-생성-중지)

#### 검증 근거와 후속 확인

연결된 명세·기록에 적힌 검증 시점과 대역/실모델·로컬/운영 범위를 확인한다. 이 상세 정리는 새 테스트 통과를 의미하지 않는다. 현재 작업 상태는 위 상태 표를 기준으로 읽고, 후속 검증은 승인된 범위에서 수행한 뒤 결과와 상태를 함께 갱신한다.

### 관리자 사용자 관리

작업 ID: `admin-user-management`
<a id="admin-user-management"></a>

#### 배경과 목적

여러 사람이 각자의 계정으로 서비스를 사용해야 할 때 관리자가 계정을 운영할 수 있어야 한다. 개인 계정 하나로 사용하는 상황에서는 필요성이 낮으므로 필요성과 도입 시점을 먼저 판단한다.

#### 현재 상태

로그인·내 정보 조회·토큰 갱신과 역할 검사는 제공한다. 기본 시드 로그인 계정은 admin·viewer이며, user 역할 값이 있다는 사실과 관리자용 사용자 관리 화면이 있다는 사실은 구분한다. 현재 프로젝트·대화는 사용자 소유권으로 접근을 제한한다.

#### 작업 범위안

- 관리 대상 계정의 목록과 상태 확인.
- 관리자의 사용자 추가.
- 기존 사용자 비활성화.
- 사용자 역할 지정·변경과 화면·서버 권한의 일관성 확인.

#### 프로젝트 공유와의 관계

계정을 추가했다고 다른 사용자의 프로젝트를 볼 수 있는 것은 아니다. 계정 관리와 프로젝트 공유의 필요성·도입 시점은 각각 판단한다. 공유를 도입할 때에는 대상 사용자와 열람·편집 범위를 별도로 정의한다.

#### 결정할 사항

- 관리자 직접 생성과 초대 중 어떤 방식으로 계정을 만들지.
- 최초 비밀번호 설정·재설정 방식.
- 관리자가 관리할 수 있는 사용자의 범위.
- 비활성화 시 기존 Access·Refresh 세션의 처리 시점.
- 비활성 사용자가 소유한 프로젝트·대화의 보관과 접근 정책.
- 자기 계정 및 마지막 관리자 계정의 비활성화·역할 변경 허용 여부.

#### 완료 판단 기준안

정책을 확정한 뒤 관리자에게 허용된 계정 조작이 가능하고 비관리자의 조작은 서버에서 거부되는지 확인한다. 중복 계정·허용되지 않은 역할 변경을 처리하고, 비활성화·역할 변경이 확정한 인증 정책에 반영돼야 한다. 사용자 관리 조작으로 프로젝트 공유 권한이 생기지 않아야 한다.

#### 관련 문서

- [현재 로그인·세션·역할](features/auth.md)
- [현재 프로젝트·대화](features/projects-conversations.md)

현재 계정은 시드 2개(`admin`·`viewer`)뿐이고 로그인·내 정보 조회만 있다. 관리자가 사용자 추가·비활성화·역할 지정. 프로젝트 공유 등 권한 정합은 사용자 관리 이후에 함께 정리. 추가(2026-10-14): 여러 계정 운영·같은 프로젝트 공동 열람이 필요할 때 의미가 있고 개인 사용이면 불필요. 계정 관리와 공유는 각각 판단

### DB 구조 파악(ERD)

작업 ID: `database-map`
<a id="database-map"></a>

#### 배경과 목적

컬럼·PK·선언된 FK만으로 질문의 업무 의미와 관계를 해석하기 어려운지 확인한다.

#### 검토할 작업 범위

실제 오답 질문을 기준으로 빠진 관계·테이블 설명·업무 용어를 정리한다. 그 정보의 보관·갱신과 ERD 화면의 필요성을 각각 검토한다.

#### 결정할 사항

- 어떤 질문이 현재 구조 정보만으로 실패하는지.
- 선언된 FK 외 관계를 누가 확인할지.
- 스키마 변경을 언제 감지·반영할지.
- 영속 지도·ERD·자동 추론 중 필요한 범위.

#### 완료 판단 기준안

대표 질문에서 부족한 구조 정보를 설명하고 필요한 보완 범위를 결정한다. 지도를 구현할 경우 갱신 전후 SQL 해석이 개선되는지 확인한다.

#### 관련 문서

[DB 연결과 권한](features/admin.md), [SQL 계획·실행](features/chat.md)

#### 기존 계획·논의 기록

DB 연결 시 AI가 쓸 DB 지도(테이블 관계·설명·용어)를 만들어 보관하고 스키마가 바뀌면 갱신. SQL 정확도와 필터 연결 판단의 기반. 현재는 질문마다 컬럼·PK·선언된 FK만 읽는다. 추가(2026-10-14): 컬럼·PK·FK로 부족한 관계·설명·업무 용어 보완의 가치부터 확인. 영속 DB 지도·ERD 화면·자동 관계 추론 전체는 필수 아님

틀린 결과끼리의 일치와 실제 정답 일치를 구분하고, 오류가 표현·기간·집계 중 어디에서 생겼는지 기록한다.

### 위젯 표현(옵션) 수정 (채팅·수동)

작업 ID: `widget-presentation-editing`
<a id="widget-presentation-editing"></a>

#### 배경과 목적

이미 만든 위젯의 표현만 바꾸기 위해 데이터 질문을 처음부터 반복하지 않도록 한다.

#### 검토할 작업 범위

대상 위젯 선택과 변경할 표현을 특정하고 채팅·수동 입력으로 기존 위젯을 수정하는 흐름을 검토한다. 전체 옵션·전체 이력의 일괄 구현은 요구하지 않는다.

#### 결정할 사항

- 처음 지원할 표현.
- 수정 대상 식별 방식.
- 데이터 재조회가 필요한 변경과 표현만 바뀌는 변경의 경계.
- 허용 옵션과의 연결.

#### 완료 판단 기준안

선택한 위젯에 의도한 표현 변경이 반영되고 다른 위젯이나 조회 조건을 잘못 바꾸지 않는다.

#### 관련 문서

[위젯 정의와 표시](features/widgets-artifact.md), [Stage 저장](features/stage.md)

생성된 위젯의 표현만 고치려고 질문을 다시 하지 않도록, 이미 만든 위젯을 채팅으로 요청하거나 직접(수동) 조작해 바로 수정하는 방법. 모든 옵션과 전체 변경 이력을 한꺼번에 하지 않는다

#### 배경과 목적

저장한 Stage를 재사용할 때 반복해서 바꾸는 조회 조건을 식별한다.

#### 검토할 작업 범위

같은 위젯의 기간·차원을 바꿔 다시 조회하는 최소 범위를 먼저 비교한다. 값 보내기·받기, 전역 필터·드릴다운은 필요성과 연결 범위를 따로 정한다.

#### 결정할 사항

- 반복 변경할 조건.
- SQL 조회 정의의 입력 자리.
- 전달 값 검증.
- 범용 연결의 필요성.
- 핵심 필요성과 구현 범위에 관한 기존 이견.

#### 완료 판단 기준안

선택한 조건 변경이 조회 결과에 반영되고 허용되지 않은 입력이 SQL 실행 경로에 섞이지 않는다. 필요성·범위에 대한 결정을 기록한다.

#### 관련 문서

[현재 데이터 조회](features/widgets-artifact.md), [Stage](features/stage.md)

#### 기존 계획·논의 기록

래퍼끼리 값을 주고받는 구조. 전역 필터·위젯 간 제어·드릴다운은 값을 내보내면 연결된 위젯이 다시 조회하는 같은 동작이다. 조회 정의에 필터를 받을 자리를 마련하는 것이 전제. 추가(2026-10-14): 최소 범위는 같은 위젯의 기간·차원만 바꿔 다시 조회하는 것. 범용 위젯 연결·드릴다운은 필수 아님. 어떤 조건을 반복해서 바꿀지 좁혀 비교한다. 분류 이견: 필요성 높음(Stage 재사용의 핵심) / 범위 판단

### 다시 생성·계속하기·메시지 개별 삭제

작업 ID: `chat-turn-actions`
<a id="chat-turn-actions"></a>

#### 목적과 사용자 동작

답변/위젯/처리 내역 아래에서 다시 생성하거나 저장된 요청을 이어가고, 질문과 답변 각각에 삭제 버튼을 제공해 선택한 메시지 한 개만 삭제한다.

#### 구현 범위와 경계

질문은 중복 저장하지 않고 답변을 원래 질문에 연결한다. 과거 답변은 보존하며 최신 답변과 이어진 결과로 다음 문맥을 구성한다. 계속하기는 저장된 채팅 기반이며 미저장 모델 실행 상태의 복원이 아니다. 삭제는 선택한 메시지 한 개에만 적용하고 다른 질문·답변과 프로젝트 자원을 보존한다. 질문 삭제 시 남은 답변을 다른 질문에 연결하지 않는다. [기능](features/chat.md#답변-다시-생성계속하기메시지-개별-삭제), [기록](temp/chat-turn-actions-2026-10-15.md).

#### 검증 범위

대역 API/문맥 테스트·PostgreSQL 트랜잭션 삭제/동시 요청 보호 테스트·프런트 질문 연결 테스트를 작성했다. 아직 실행하지 않았다. 브라우저 검증·실모델 호출·배포도 수행하지 않았다.
